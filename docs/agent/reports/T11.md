# T11. Исправления по аудиту безопасности

## Статус
Выполнено

## Что сделано

### a) SSRF через webhook_url
- `src/payment_service/entrypoints/api/schemas.py`: входная валидация `webhook_url`.
  Разрешён только `https`; `http` — только при `WEBHOOK_ALLOW_HTTP=true` (по умолчанию `false`).
  Отклоняются IP-литералы (IPv4/IPv6), `localhost` и `*.localhost`, URL с userinfo
  (`user:pass@`). Ошибки проходят через общий обработчик и возвращаются как
  `422 {"error": {"code": "validation_error", ...}}`.
- `src/payment_service/infrastructure/webhook.py`: проверка при отправке.
  - `asyncio.get_running_loop().getaddrinfo` резолвит хост перед каждым запросом
    (повторный резолвинг, а не кэш, поэтому DNS rebinding не обходит проверку).
  - Любой loopback/private/link-local/multicast/reserved/unspecified адрес отклоняется
    (`ipaddress`); для IPv6 дополнительно проверяется `ipv4_mapped`
    (`::ffff:127.0.0.1`).
  - `WEBHOOK_ALLOWED_HOSTS` (comma-separated, нормализуется в `Settings.webhook_allowed_host_names`)
    позволяет пропустить проверку адресов для доверенных хостов; по умолчанию список пуст.
  - Отклонение — отдельное исключение `WebhookDestinationForbidden`.
  - `follow_redirects=False` задан и на клиенте, и явно в каждом `post`.
  - Неразрешимый хост — обычная сетевая ошибка (`httpx.ConnectError`), а не запрет:
    такие ошибки по-прежнему идут в retry.
- `src/payment_service/entrypoints/consumer.py`: `WebhookDestinationForbidden`
  обрабатывается отдельной веткой — сообщение сразу публикуется в `payments.dlx` →
  `payments.dlq` (без retry), с причиной в `x-last-error`. Статус платежа к этому
  моменту уже сохранён и не меняется. Публикация в DLQ вынесена в
  `publish_to_dead_letter` и переиспользуется исчерпанием попыток.
- `docker-compose.yml`: `WEBHOOK_ALLOW_HTTP` и `WEBHOOK_ALLOWED_HOSTS` прокинуты в
  `consumer`; `WEBHOOK_ALLOW_HTTP` — также в `api`, потому что входная валидация
  выполняется в API-процессе. `WEBHOOK_ALLOWED_HOSTS` в API не нужен.
- `.env.example`: безопасные значения по умолчанию (`WEBHOOK_ALLOW_HTTP=false`,
  `WEBHOOK_ALLOWED_HOSTS=`). Для e2e значения задаются только через окружение
  (см. README): `WEBHOOK_ALLOW_HTTP=true`, `WEBHOOK_ALLOWED_HOSTS=e2e-webhook-receiver`.

### b) API-ключ без значения по умолчанию
- `src/payment_service/config.py`: `api_key: SecretStr` без default. Валидатор
  отклоняет пустой/пробельный ключ, плейсхолдер `change-me` и ключи короче
  32 символов (`MIN_API_KEY_LENGTH`) с понятным сообщением и подсказкой команды
  генерации. Сервис не стартует с невалидным ключом.
- `.env.example`: `API_KEY=change-me` и комментарий с командой генерации; старый
  ключ `jhA4bsjJK5hdbf6` удалён из `.env.example` и `config.py`.
- `README.md`: генерация ключа — обязательный шаг **внутри** инструкции по запуску,
  между `cp .env.example .env` и `docker compose up`. Явно описано, что без замены
  ключа сервис намеренно не стартует.
- Тестовый ключ в `tests/conftest.py` и fallback в `tests/e2e/test_flow.py` —
  длиной ≥ 32 символов.
- В `docker-compose.yml` `API_KEY` добавлен в `migrations`, `outbox-relay` и
  `consumer`: их код импортирует `Settings`, где ключ теперь обязателен.
- `alembic/env.py` тоже импортирует `Settings`, поэтому сервис `migrations` получает
  `API_KEY` из compose.

### c) Непривилегированные контейнеры
- `Dockerfile`: пользователь `app` с фиксированным UID 10001, `chown -R app:app /app`,
  `USER app`. Версия uv зафиксирована (`pip install uv==0.13.9`).
- `docker-compose.yml`: для `api`, `consumer`, `outbox-relay`, `migrations` —
  `security_opt: [no-new-privileges:true]`, `cap_drop: [ALL]`, `read_only: true`,
  `tmpfs: /tmp` (YAML-anchor `x-hardened`). Проверено на полном стеке: все четыре
  сервиса работают с read-only rootfs, отключать `read_only` не потребовалось.

### d) Ограничение размера входных данных
- `schemas.py`: `MAX_METADATA_BYTES = 16 * 1024`, `MAX_METADATA_DEPTH = 5`.
  Сериализованный JSON `metadata` (UTF-8) и глубина вложенности проверяются в
  одном валидаторе; превышение → `422`.
- Проверено, что `description` ограничен 500 символами, а `Idempotency-Key` —
  255 символами и непустым значением (без изменений).

### e) Попутно
- `.env.example` и compose: пароли PostgreSQL/RabbitMQ заменены на `change-me`;
  compose требует их явной установки через `${POSTGRES_PASSWORD:?...}` и
  `${RABBITMQ_DEFAULT_PASS:?...}`, как и `API_KEY`. README описывает замену.
- `Dockerfile`: фиксированная версия `uv==0.13.9` (версия из окружения).
- `README.md`, раздел «Что не является production-ready»: добавлены HMAC-подпись
  webhook, rate limiting и защита от перебора ключа как известные ограничения;
  перечислены реализованные меры (SSRF-защита, обязательный сильный ключ,
  непривилегированные контейнеры, лимиты входных данных).
- README дополнен описанием лимитов и SSRF-поведения, командой e2e с настройкой
  allowlist и требованием валидного `API_KEY` для запуска тестов из Python.

### Дефекты, найденные и исправленные в ходе проверок
- `asyncio.getaddrinfo` не существует (это метод event loop): первый e2e-прогон
  на новом образе дал `AttributeError: module 'asyncio' has no attribute
  'getaddrinfo'`. Резолвер переведён на `loop.getaddrinfo`; добавлен unit-тест
  `test_default_resolver_uses_event_loop_getaddrinfo`, который выполняет реальный
  резолвинг `localhost`.
- E2E-приёмник webhook запускается тем же образом от UID 10001 и не мог писать
  в bind-mounted каталог: в `tests/e2e/test_flow.py` каталог теперь `chmod 0o777`.
- Для e2e приёмник получил фиксированное имя `e2e-webhook-receiver`
  (`E2E_WEBHOOK_HOST`), чтобы попадать в `WEBHOOK_ALLOWED_HOSTS`; тест пропускается,
  если consumer не настроен на этот хост.

## Проблемы и вне scope
- Остаётся TOCTOU между резолвингом и фактическим подключением: httpx резолвит имя
  повторно. Полное устранение требует подключения по проверенному IP с сохранением
  Host/SNI; в рамках T11 не делалось.
- `WEBHOOK_ALLOWED_HOSTS` полностью обходит проверку адресов для указанных имён —
  это осознанный доверенный список, по умолчанию пустой.
- `ruff format --check` по-прежнему расходится с существующим кодом (pre-existing,
  проект проверяет `ruff check`).
- Интеграционные тесты создают схему через `Base.metadata.create_all/drop_all`,
  а не через Alembic; после них в БД остаётся `alembic_version`, поэтому
  `alembic downgrade base` на такой БД падает. Миграции проверяются на чистой БД.
- Смена `POSTGRES_PASSWORD`/`RABBITMQ_DEFAULT_PASS` не применяется к уже
  инициализированному тому PostgreSQL — после смены пароля нужен `docker compose down -v`.
- HMAC-подпись webhook, rate limiting и защита от перебора ключа не реализованы
  (описаны в README как известные ограничения).

## Вердикт
Готово к сдаче. Линтер, unit/архитектурные, интеграционные, rabbit- и e2e-тесты
зелёные; миграции проходят полный цикл на чистой БД; чистый клон без замены ключа
намеренно не стартует с понятной ошибкой, а с ключом и паролями по README поднимается
полностью; контейнеры работают от UID 10001 с read-only rootfs и без capabilities;
SSRF- и metadata-проверки возвращают 422, отсутствие ключа — 401, запрещённый адрес
на отправке уходит в DLQ без retry; старый ключ в репозитории отсутствует.
